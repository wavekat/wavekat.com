The browser gives up

A phone link is a URI, not an action. Your browser has no idea how to place a phone call — so it hands the string to the operating system and asks someone else to deal with it.

<a href="tel:+14155550123">(415) 555-0123</a>

Which means: a clicked phone link is a request from an untrusted party, delivered to your app as a string. Everything else follows from taking that sentence literally.

A tel: URI is messier than it looks

tel:+1-415-555-01.23;phone-context=example.com

tel: — the scheme. Also sip:, for a SIP address rather than a number.

+ — may arrive percent-encoded as %2B, because it travelled through URL machinery.

- ( ) .   — visual separators. RFC 3966 allows them. Phone books are full of them.

;phone-context=… — parameters. Everything after the first semicolon.

Four decisions worth stealing

  • Strip control characters, don't reject on them. A stray \r shouldn't kill a valid link — but it has no business surviving downstream either.
  • The parameter cut is also an injection cut. Everything after the first ; is a parameter by spec. Correctness and safety pointing the same way.
  • Validate shape; never sanitize toward validity. A parser that rescues malformed input eventually rescues something it shouldn't.
  • The off-switch is your preference, not the OS association. Deregistration is best-effort on Linux. Gate the behaviour yourself.

War story

The deb that reported failure
while working perfectly

01Click-to-call is completely dead on Debian. The toggle refuses to turn on.
02…but the OS was routing tel: links correctly the whole time. Since install.
03xdg-settings verifies by resolving the desktop name back to a binary — with a naive first_word() of the Exec line.
Exec="/opt/WaveKat Voice/@wavekatvoice-desktop" %U

It splits inside the quote. which fails. xdg-settings exits 2. Electron reports false. The preference is only persisted on success — so it never saved, and the dispatch gate dropped every clicked link.

A space in a product name broke click-to-call on an entire platform.

The fix: ask a question the tool can answer

xdg-settings check has the same defect, so isDefaultProtocolClient is no help either. But the query side of xdg reports the current handler's name instead of resolving a name back to a binary — and it has no such bug.

execFileSync("xdg-mime", ["query", "default", `x-scheme-handler/${scheme}`])
  .trim() === `${basename(process.execPath)}.desktop`

On Linux, a false isn't taken at face value — it's confirmed against xdg-mime query, and a match counts as success.

What generalizes

  • Declaring and claiming are different operations with different consent requirements.
  • There are three delivery paths, not one. The one you'll forget is “already running” — the most common one in real use.
  • The handler entry point is an untrusted-input boundary. Allowlist, cap, validate, reject.
  • Never let the OS association be your off-switch.
